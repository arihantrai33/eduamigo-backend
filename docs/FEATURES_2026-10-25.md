# Features added on 25 October 2026

What was built, how it behaves, how to configure it, and what is **not** verified. Nothing here is committed or deployed.

## Profile photos for every role
- `PUT /api/users/me/avatar` (multipart `photo`: JPEG, PNG or WebP, up to 5 MB, checked by the file's bytes) and `DELETE /api/users/me/avatar`.
- A **student's** photo is the one on the student record (`Student.photoKey`), so the school's lists, the ID card and every portal show it at once.
  Everyone else's is `User.avatarKey` (private, never returned by the API; the API returns a short-lived signed link, `/api/photos/<token>`).
- Teacher lists and the chat inbox show a person's own photo. A support session cannot change a photo.
- Storage: Cloudinary (authenticated assets). **Local demo and development** have no Cloudinary: set `PHOTO_STORAGE=local` (the demo script does this
  when `CLOUDINARY_CLOUD_NAME` is empty); files go to `.dev-uploads/` (ignored by git). Never set it in production.

## Files in homework and chat (`services/attachments.js`)
- Photos, PDFs, voice notes (webm, ogg, mp3, m4a, wav), Word, Excel, PowerPoint and plain text, up to 10 MB each. The **bytes** decide the type
  (`utils/fileType.js`); HTML, SVG, scripts and executables are refused.
- Stored privately under `eduamigo/<school>/files/<homework|chat>/…`; served by `GET /api/files/<token>` (signed, expires, always sent as a download
  with the type the server chose, `nosniff`, and a sandbox policy except for PDFs, which need the browser viewer).

## Homework (`/api/homework`)
- A teacher (anyone with `notes.upload`, only for the classes they teach) gives homework to a whole class (optionally one section), to **chosen
  students** of it, or to **one student**. Title, subject, instructions, due date (not in the past), up to 3 files.
- Students and parents are notified. `GET /my` (student), `GET /child` (parent), `POST|DELETE /:id/done` (student), `GET /` and `GET /:id` (staff:
  a teacher sees what they gave, the office sees all; the detail lists who has finished), `DELETE /:id`.
- Homework is a **core module** (no plan gating), governed by the study-material permission.

## Chat
- `GET /api/chat/inbox`: everyone the signed-in user may message, in one shape (photo, role, subtitle, unread count, last message, class), most
  recent first. Students see their teachers and the office; parents the same for the selected child's class; teachers their classes' students,
  parents and the office; the office everyone.
- `POST /api/chat/messages` takes multipart (`text`, up to 2 `files`) as well as the old JSON. Photos, files and voice notes come back as signed links.
- The chat screen refreshes by polling (messages every 3 s while a chat is open, the inbox every 8 s). There is no WebSocket layer.

## Concerns raised with parents (`/api/complaints`)
- Staff (a teacher for their own students, the office for anyone) raise a concern about a student: type, subject, details. Parents are notified,
  see it under Chat > Concerns, and reply; the school replies, closes (`resolved`) and reopens it.

## Sign-in with a one-time code, and password reset by code
- `POST /api/users/otp/request` `{ schoolCode, identifier }` and `POST /api/users/otp/verify` `{ schoolCode, identifier, code }`. The same answer is
  given whether or not the account exists. Codes are 6 digits, hashed, valid 10 minutes (reset: 15), five wrong tries then gone, one new code per
  minute and at most six an hour per account. A signed-in-by-code person no longer has to change a temporary password first.
- Delivery: to the mobile number when the person typed one **and SMS is live** (provider enabled, production mode), otherwise to the email on file,
  and to the other channel when the first is missing. With SMS in test mode and no email, the code is printed in the **server console only**
  (never in production, never in an API answer).
- Password reset by code uses the same delivery (previously email only).
- **Not verified**: real SMS to a phone (needs a provider account and, in India, DLT registration of the sender and template) and real email through
  Gmail, SES, Resend or Brevo (needs credentials entered in the owner console). Both paths are covered by tests with the providers replaced.

## Sessions
- A sign-in lasts 24 hours (`JWT_EXPIRES_IN` overrides). Signing out everywhere or a password reset ends sessions earlier, as before.
- Passkeys were **not** built (deferred on request).

## Live bus
- The line on the map and the bus follow the **road**: when a trip starts, or when a trip is found without a road (for example the routing service was
  down), the road through the stops is fetched once and saved. `MAPBOX_ACCESS_TOKEN` (Mapbox Directions) is used when set, otherwise an
  OSRM-compatible service (`ROUTING_URL`; the public demo server is for trying only; `off` disables it).
- A reading counts as "on the road" up to the phone's reported accuracy × 1.5 (at least 50 m, at most 120 m), so the bus stays on the street.
- "On route" is shown only when the driver's phone is sending its position (`tripSignal` in `/transport/my-child-bus`): started but silent shows
  "Started, waiting for GPS"; a silent bus shows "Location lost".
- The demo no longer seeds a bus as "On Route". To watch one move: `node src/scripts/simulateBus.js <driverToken> --api http://localhost:8000/api`.

## Owner console (earlier in the same programme)
- Roles: owner (everything), billing, support, viewer (read only). An account with no role is an owner. `GET /api/platform/roles`.
- Plan changes: `POST /api/platform/schools/:id/subscription/preview` shows what a change would do before it is applied.
- Replies to support requests are emailed to the school office (best effort; the owner sees whether it was sent).
